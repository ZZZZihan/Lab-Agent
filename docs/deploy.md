# Production Deployment Guide (`docs/deploy.md`)

This guide covers hardening, network topology, first-admin bootstrap, and backup procedures when deploying Lab Agent in a production lab environment (`APP_ENV=prod`).

---

## 1. Network Exposure & Reverse Proxy (Expose Only `web`)

- **Do not expose internal services**: In production, `postgres` (`5432`), `redis` (`6379`), and `api` (`8000`) must stay on the internal Docker bridge network or bind strictly to `127.0.0.1` (`127.0.0.1:43124:8000` only if host-local debugging is needed). Never publish `postgres`, `redis`, or `api` ports on `0.0.0.0`.
- **Host-side model services stay loopback-only**:
  - **Ollama** (`127.0.0.1:11434`): Keep `OLLAMA_HOST` unset so Ollama binds only to `127.0.0.1`. Containers reach it via `http://host.docker.internal:11434/v1`.
  - **Magpie Gateway** (`127.0.0.1:3425`): Keep bound to loopback or firewall-restricted internal interfaces; authenticate using a dedicated Lab Agent key file mounted at `/run/secrets/magpie_key` (`chmod 600 ~/.config/lab-agent/magpie.key`).
- **TLS Reverse Proxy in front of `web`**:
  - Place a TLS-terminating reverse proxy (e.g., Caddy or Nginx) in front of `127.0.0.1:43123` (`web:3000`).
  - Configure the reverse proxy to overwrite/set `X-Forwarded-For` with the true client IP and `X-Forwarded-Proto: https`. Next.js route handlers sign and forward the client IP to `api` using `X-Client-IP` + `X-Internal-Proxy-Secret` so login rate limiting and HMAC-hashed IP auditing reflect the real client address.

Example Caddyfile:
```caddyfile
lab-agent.internal.example.org {
    tls internal
    reverse_proxy 127.0.0.1:43123 {
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
    }
}
```

## 2. Production Environment Configuration (`APP_ENV=prod`)

Generate a baseline `.env` with `./scripts/init-env.sh` and update the production settings before starting the stack:

| Variable | Production Requirement |
| --- | --- |
| `APP_ENV` | Set to `prod`. Enables fail-closed startup checks and disables demo seed fixtures (`app.seed`). |
| `COOKIE_SECURE` | Set to `true` (both in `.env` and on the `web` service) so session cookies carry the `Secure` attribute over HTTPS. |
| `NEXT_PUBLIC_DEMO_HINTS` | Build and run `web` with `NEXT_PUBLIC_DEMO_HINTS=false` so the login page does not prefill demo accounts. |
| `CORS_ORIGINS` | Set to the exact HTTPS origin of the deployment (e.g. `https://lab-agent.internal.example.org`). Wildcards (`*`) are rejected when `APP_ENV=prod`. |
| `JWT_SECRET` | High-entropy random secret ($\ge 32$ chars, generated by `init-env.sh`). |
| `INTERNAL_PROXY_SECRET` | Required when `APP_ENV=prod`. High-entropy shared secret between `web` and `api` for `X-Client-IP` verification. |
| `AUDIT_HMAC_KEY` | Required when `APP_ENV=prod`. Dedicated high-entropy HMAC key used by `hash_ip` for `audit_events.ip_hash`. |
| `POSTGRES_PASSWORD` | Strong random password for PostgreSQL (`labagent` role). |
| `REDIS_PASSWORD` / `REDIS_URL` | Strong random password for Redis (`--requirepass ${REDIS_PASSWORD}` and `redis://:${REDIS_PASSWORD}@redis:6379/0`). |
| `LLM_API_KEY_FILE` | Mounted via Docker secret at `/run/secrets/magpie_key` from host `~/.config/lab-agent/magpie.key` (`0600`). |
| `EMBEDDING_MODEL_VERSION` | Required when `APP_ENV=prod` and `EMBEDDER != hashing`. Pin to the exact Ollama model digest from `ollama list`. |

## 3. Non-Root Containers & Supply Chain

- **`api` container**: Runs as non-root user `labagent` (`uid=10001`, `gid=10001`), with `/app/data/uploads` and `/app/data/calibrations` owned by `10001:10001`. Verify after startup:
  ```bash
  docker compose exec api id -u
  # Expected output: 10001
  ```
- **`web` container**: Runs as the built-in non-root `node` user (`uid=1000`).
- **Pinned digests & scanning**: Base images in `backend/Dockerfile` and `frontend/Dockerfile` are pinned by SHA-256 manifest digest and tracked by Dependabot (`.github/dependabot.yml`). CI scans both built images with Trivy (`HIGH`/`CRITICAL` with fixes fail the build) and publishes SPDX SBOM artifacts.

## 4. First-Admin Bootstrap

When `APP_ENV=prod`, `api-entrypoint.sh` skips `python -m app.seed` and refuses to load demo accounts (`LabAgent-Demo-2026-*`). Bootstrap the initial administrator account via `app.admin_cli`:

```bash
# Prompts or reads the initial admin password from stdin (must be >= 12 chars, >= 3 char classes)
printf '%s\n' 'Your-Strong-Admin-Password-2026!' | \
  docker compose exec -T api python -m app.admin_cli create-user \
    --email admin@your-lab.org \
    --name "Lab Administrator" \
    --role admin \
    --password-stdin
```

After signing in as the administrator, additional users and project groups can be managed either from the Web UI (`/admin/users`, `/admin/groups`) or via `python -m app.admin_cli`.

## 5. Backups, Retention & Integrity Verification

1. **PostgreSQL Database (`pgdata`)**:
   - Run daily logical backups with `pg_dump` (includes documents, chunks, ACLs, users, groups, conversations, and the append-only `audit_events` table):
     ```bash
     docker compose exec -T postgres pg_dump -U labagent -Fc labagent > "labagent_$(date +%Y%m%d_%H%M%S).dump"
     ```
   - Test restoration periodically into a staging instance with `pg_restore -U labagent -d labagent --clean --if-exists`.
2. **Calibration & Upload Volumes (`calibrations`, `uploads`)**:
   - Back up `/app/data/calibrations` (or the committed `evals/calibrations/*.json` files) and `/app/data/uploads`.
3. **Secret Keys (`~/.config/lab-agent/magpie.key` & `.env`)**:
   - Store `JWT_SECRET`, `INTERNAL_PROXY_SECRET`, `AUDIT_HMAC_KEY`, `POSTGRES_PASSWORD`, and `REDIS_PASSWORD` in your organization's secret manager / encrypted backup vault. Note that rotating `AUDIT_HMAC_KEY` intentionally prevents correlating new `ip_hash` values with older audit records.
4. **Audit Hash-Chain Verification**:
   - Verify tamper-evidence of the append-only `audit_events` log before and after maintenance windows:
     ```bash
     docker compose exec -T api python -m app.admin_cli verify-audit
     ```
   - Periodic retention cleanup runs automatically every `MAINTENANCE_INTERVAL_SECONDS` (default `86400`s) under a Redis distributed lock (`maintenance:lock`).
